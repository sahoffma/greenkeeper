## 2. Ausgangslage

Greenkeeper implementiert Düngerbestand heute als **Gebinde-Modell**:

| Ebene | Ist-Stand (Repository `bc49546` / `e14522d`) |
|-------|-----------------------------------------------|
| **Tabelle Inventory Item** | `public.fertilizer_containers` — Kommentar/Migration: „physisches Gebinde“ |
| **Tabelle Movement** | `public.fertilizer_stock_movements` — append-only, `movement_at` kanonisch |
| **Creation** | `create_fertilizer_inventory_core_from_confirmed_packages` — **ein Item pro Packung** in Schleife |
| **Zugang** | Initiale positive Movement pro neuem Item (`initial_stock`, `purchase`, `gift_received`) |
| **Bestandsliste** | Client: `fetchFertilizerStockList` — **ein Listeneintrag pro Container**, Saldo je Item |
| **Düngung** | Route `/ausruestung/duenger/:inventoryItemId/anwenden`, RPC `apply_fertilizer_inventory_item_to_areas` |
| **Constraint Düngung** | Unique Index `fertilizer_stock_movements_application_batch_idx` — **genau ein Movement pro Batch** (kompatibel mit DL-033) |
| **Unique Produktbestand** | **Kein** Unique Constraint auf `(user_id, saved_product_profile_id, base_unit)` — nur Indizes |

[DL-033](../decisions/dl-033.md) definiert das **Zielbild Version 1**: ein Inventory Item = **Produktbestand**, kein Gebinde, keine FIFO, Startseite als Tätigkeitseinstieg.

## 3. Zielvertrag (DL-033, technisch)

| Regel | Ziel |
|-------|------|
| Inventory Item | Ein **kompatibler mengenmäßiger Produktbestand** pro Schlüssel |
| Gebinde | **Nicht** modelliert; Packungsgröße nur Zugangsmengen-Eingabe |
| Zugang | Positive Movement auf **bestehendem oder neu angelegtem** Produktbestand |
| Düngung | **Genau eine** negative Movement; **ein** Batch; Mehrflächen unverändert |
| Bestand | Summe Movements mit `movement_at IS NOT NULL`; **kein** `currentQuantity` |
| FIFO / Gebindestatus | **Nicht** in Version 1 |
| Startseite | Primärer Einstieg „Düngung erfassen“ |
| Ausrüstung | Bestand/Nachschlage; **kein** primärer „Anwenden“-Button |
| Parallele Logik | **Verboten** — ein Flow, ein RPC |

## 4. Ist-Architektur (Detail)

### 4.1 Datenmodell

**`fertilizer_containers` (Inventory Item)**

- PK `id`; `user_id`; `saved_product_profile_id` (FK `product_profiles`, `profile_status = saved`)
- `access_kind` (`authenticated_user` | `session`); `base_unit` (`kg` | `ml`)
- `package_size_value` / `package_size_unit` — nominale Packung
- Legacy: `product_id`, `recognition_candidate_id`, `label`
- Kein `product_form` auf Container — Form über Join `product_profiles.product_form`
- Keine Spalte `product_version_id`
- Saldo: abgeleitet aus Movements

**`fertilizer_stock_movements`**

- `container_id` → Item; `quantity_delta`; `unit`; `movement_type`; `movement_origin`
- `movement_at` — kanonisch für Saldo
- `application_batch_id` — FK zu `fertilizer_application_batches` (unique wenn gesetzt)
- Immutability: Trigger `prevent_fertilizer_stock_movement_update/delete`

**Application / Journal**

- `fertilizer_application_batches` — 1 pro Düngung; `inventory_item_id`, Idempotenz
- `fertilizer_application_areas` — je Fläche
- `activities` + `fertilization_details` — je Fläche; Snapshots
- RPC: `apply_fertilizer_inventory_item_to_areas(p_inventory_item_id, p_saved_product_profile_id, …)`

**Saved Product Profile**

- `product_profiles.profile_status = 'saved'` — **immutable** (Trigger `prevent_saved_product_profile_mutation`)
- Repräsentiert konkrete Produktversion ([DL-018](../decisions/dl-018.md))
- `product_form` (`granular` | `liquid`) auf Profil

### 4.2 Erstellung und Zugang

- **RPC:** `create_fertilizer_inventory_core_from_confirmed_packages(p_saved_product_profile_id, packages[], reason, …)`
- Schleife: **pro Packung** INSERT Container + INSERT initiale positive Movement
- Receipt/Idempotenz: `fertilizer_inventory_creation_receipts`
- Client: `fertilizerInventoryCreation*.ts`, Capture-Integration

### 4.3 Bestandsanzeige

- `fetchFertilizerStockList()` — lädt alle Container, berechnet Saldo je Item
- `FertilizerCategoryPage` — Listeneintrag je Item, Text „Gebinde …“, Link **„Anwenden“**
- Keine serverseitige Aggregation nach Produktbestandsschlüssel

### 4.4 Düngung

- `FertilizerApplicationPage` — `useParams().inventoryItemId` Pflicht
- Flow-Core: `fertilizerApplicationFlowCore.ts`, Multi-Area: `fertilizerMultiAreaApplication*.ts`
- Submit: `applyFertilizerInventoryItemToAreas` → RPC mit `p_inventory_item_id`
- Eligibility: Core-gebundenes Item (`saved_product_profile_id`, `access_kind`, `base_unit`)

### 4.5 Startseite

- `HomeScreen`, `HomeVoiceSection` — Sprache/Text dokumentiert ([home-experience](../playbook/home-experience.md))
- **Kein** dedizierter CTA „Düngung erfassen“ mit Produktauswahl
- `homeVoiceFlow.ts` — Intent-Struktur vorhanden, Düngung noch nicht an Mehrflächen-RPC angebunden

| # | Ist | Soll (DL-033) |

## 6. Produktbestandsschlüssel

### 6.1 Fachlicher Schlüssel (DL-033)

```
(user_id, saved_product_profile_id, form, base_unit)
```

### 6.2 Persistierte Felder (Ist)

| Komponente | Persistenz | Quelle |
|------------|------------|--------|
| `user_id` | ✅ | `fertilizer_containers.user_id` |
| `saved_product_profile_id` | ✅ | `fertilizer_containers.saved_product_profile_id` |
| `form` | ⚠️ indirekt | `product_profiles.product_form` (immutable wenn `saved`) |
| `base_unit` | ✅ | `fertilizer_containers.base_unit` |

**Keine** Spalte `product_version_id`. **Keine** neue Spalte in Phase 1 erfinden, sofern Gate A grün.

### 6.3 Empfehlung Unique Constraint (Gate A)

```sql
-- Konzeptionell (Umsetzung Phase 2):
UNIQUE (user_id, saved_product_profile_id, base_unit)
WHERE access_kind = 'authenticated_user'
  AND saved_product_profile_id IS NOT NULL
  AND archived_at IS NULL
  AND stock_kind = 'product_stock'  -- optional, siehe Migration
```

**Begründung:** `saved_product_profile_id` bindet **immutable** an genau eine `product_form` ([DL-018](../decisions/dl-018.md), Trigger auf `saved`). `base_unit` ist redundant zu Form nur insofern, als DB bereits `granular→kg`, `liquid→ml` erzwingt — **beide** im Schlüssel dokumentieren, Unique technisch auf `(user_id, saved_product_profile_id, base_unit)`.

**Session-Scope** (`access_kind = session`): separater Schlüssel mit `session_access_hash` — nicht Teil des authenticated Produktbestands.

## 7. Versionsanker

### Ist-Stand

- **`saved_product_profile_id`** verweist auf `product_profiles` mit `profile_status = 'saved'`
- Saved Profiles sind **unveränderlich** (`prevent_saved_product_profile_mutation`)
- Neue Herstellerdeklaration → **neues** Saved Profile ([DL-018](../decisions/dl-018.md)) — **keine** Zusammenführung

### Beantwortung Gate A

| Frage | Antwort |
|-------|---------|
| Reicht `saved_product_profile_id` als Produkt- **und** Versionsanker? | **Ja**, für v1 — Saved Profile = konkrete unveränderliche Produktversion |
| Kann Saved Profile später verändert werden? | **Nein** (DB-Trigger) |
| Braucht es `product_version_id`? | **Nein** in v1 — offene Ergänzung nur falls später explizite Versionstabelle eingeführt wird |

### Offene Frage (Gate A, dokumentiert)

Ob **zwei** Saved Profiles fachlich „dasselbe Produkt“ sein können, ohne dass der Nutzer es erkennt — dann entstehen **zwei** Produktbestände (**korrekt** nach DL-018/DL-033). Keine automatische Merge-Heuristik.

## 8. Zielarchitektur

### 8.1 Produktbestand

```
Produktbestand (1 × fertilizer_containers-Zeile pro Schlüssel)
  └── Movements (append-only, movement_at gesetzt)
        ├── + initial_stock | purchase | gift_received
        └── − application | gift_given | disposed | inventory_correction
              (application nur mit Application Batch / Journal)
```

Bewegungssemantik: [DL-034](../decisions/dl-034.md). Ist-Enum nutzt teils `fertilization`, `gifted_away`, `disposal` — Ausrichtung in Phase 2/6.

- Kein `currentQuantity`
- Keine Gebindeobjekte, kein FIFO
- `package_size_*` optional, nur Capture-Hilfe

### 8.2 Zugang

```
find_or_create_product_stock(user, saved_product_profile_id, base_unit)
  → atomar: SELECT … FOR UPDATE | INSERT
  → append_positive_movement(amount, reason)
```

- Idempotenz über Receipt + Movement-Key (bestehendes Muster)
- Race: Unique Constraint + Retry auf Unique Violation → Re-SELECT

### 8.3 Anwendung

```
Startseite → Produktbestand wählen → Flächen/Modus/Menge → Bestätigung
  → apply_fertilizer_inventory_item_to_areas(p_inventory_item_id = kanonische Item-ID, …)
  → 1 Batch, N Activities, 1 negative Movement
```

- **RPC-Semantik unverändert** — nur Einstieg und Item-Auflösung ändern sich
- `p_inventory_item_id` bleibt — Wert = **Produktbestands-Item**

### 8.4 Ausrüstung

- Read-only Liste: Produktname, Saldo, Base Unit
- Kein „Anwenden“; optional Produkt-/Profil-Detail
- Capture/Erfassung bleibt separater Zugang (Phase 6)

### 8.5 Journal

- Unverändert: je Area Activity; Snapshots; keine sichtbare Bestandskomplexität

## 13. Datenmigration (Strategie — Überblick)

> **Detailvertrag:** §27 (Phase 3). Dieser Abschnitt bleibt als Kurzüberblick; bei Widersprüchen gilt §27.

### Prinzipien

- **Additiv zuerst** — keine destruktive Löschung von Movements oder Items
- **Ledger unveränderlich** — kein UPDATE/DELETE/Umhängen auf `fertilizer_stock_movements` ([DL-019](../decisions/dl-019.md))
- **Historische FKs** — `fertilization_details`, `application_batches`, Journal-Snapshots **nicht** umschreiben
- **Rollback** — Archivierung + Mapping-Receipt; keine Löschung

### Duplikat-Gruppen

**Erkennung:** Gleicher Migrationsgruppenschlüssel `(user_id, saved_product_profile_id, base_unit)` — **nur** über identische `saved_product_profile_id`, nicht über Produktname oder Package Size (§27.3).

**Kanonisches Ziel:** vorhandenes aktives `product_stock`-Item **oder** neu angelegtes kanonisches Item (Phase-2-Intake-Muster).

**Legacy-Items nach Migration:** `archived_at` gesetzt; `superseded_by_container_id` → kanonisches Item; historische Movements **bleiben** am Legacy-Container.

**Saldoübernahme (empfohlen, §27.6):** Einmalige **positive Übernahmebewegung** auf dem kanonischen Item; **keine** Korrektur-Paare auf Legacy-Items; **keine** Read-Aggregation als Ersatz für Buchung.

**Verworfen für Phase 3:** Korrektur-Paare (`inventory_correction` − / `purchase` + auf zwei Items), die in frühen Entwürfen diskutiert wurden — widersprechen DL-034 und erhöhen Doppelzählungsrisiko.

### Legacy ohne Core-Bindung

- Nicht application-eligible (bestehend)
- Klasse E — keine automatische Produktbestands-Migration ([DL-030](../decisions/dl-030.md), Legacy-Upgrade-Pfad separat)

### Verbrauchte Alt-Items (Saldo 0)

- Supersede/Archivierung ohne Übernahmebewegung (Klasse J)

### Inkompatible Items

- Nicht zusammenführen; Klassen F–H blockiert (§27.12)

## 15. Idempotenz

- **Zugang:** Receipt-Tabelle analog `fertilizer_inventory_creation_receipts`; Fingerprint inkl. `saved_product_profile_id`, `quantity`, `reason`, `idempotency_key`
- **Düngung:** unverändert `fertilizer_application_batches` + `request_fingerprint`
- **Migration:** Migrations-Receipt oder `migration_batch_id` pro konsolidiertem Item-Paar — Wiederholung safe

---

## 16. Konkurrenz und Locks

| Vorgang | Mechanismus |
|---------|-------------|
| Parallele Zugänge | `SELECT … FOR UPDATE` auf kanonischem Item **oder** Advisory Lock auf `(user_id, profile_id, base_unit)`; Unique als Backstop |
| Parallele Düngungen | Bestehend: Item-Lock im RPC + Saldo-Reprüfung |
| Migration | Batch-weise; keine User-Writes während Item-Konsolidierung pro Gruppe (Maintenance-Flag optional) |

## 17. Teststrategie

### Domain (Phase 1)

- Gleicher Schlüssel; inkompatible Form/Unit/Profil
- Positiver/negativer Saldo; Präzision; unzureichender Bestand
- Find-or-create Semantik

### Persistenz (Phase 2)

- Erster Zugang erstellt Item; zweiter nutzt dasselbe
- Parallele Zugänge → kein Duplikat
- Idempotenz Replay/Konflikt
- Düngung: genau 1 Movement; Rollback; RLS; Immutability

### Migration (Phase 3)

- 1 / N kompatible Alt-Items; historische Anwendungen; verbraucht; Legacy; inkompatibel
- Movement-Summen invariant; wiederholbare Migration

### UI (Phase 4–5)

- Ausrüstung ohne Apply; Produktbestand sichtbar
- Startseiten-CTA; Ein-/Mehrflächen; Pflegegruppe; Fehler erhält Eingaben
- Kein Gebindetext

### Clean-HEAD

- Jede Phase committbar unabhängig vom lokalen WIP
- Dev-DB-Tests nur mit Opt-in ([GA-010](./ga-010.md))

### 25.4 Aktiver kanonischer Bestand

**Definition „aktiv“ (technisch, für Unique-Partial-Index):**

```text
access_kind = 'authenticated_user'
AND user_id IS NOT NULL
AND saved_product_profile_id IS NOT NULL
AND base_unit IS NOT NULL
AND archived_at IS NULL
AND stock_kind = 'product_stock'   -- neue Spalte, siehe §25.5
```

**Session-Scope** (`access_kind = session`): eigener Bestand mit `session_access_hash` — **nicht** Teil des authenticated Unique-Vertrags; separater partieller Index `(session_access_hash, saved_product_profile_id, base_unit)` optional analog.

**Legacy-Gebinde-Items** (bestehende Creation-Schleife): `stock_kind IS NULL` oder `stock_kind = 'physical_package'` — **ausgenommen** vom kanonischen Unique, bleiben lesbar bis Phase 3.

### 25.5 Unique-/Index-Strategie

#### Option A — Sofortiger vollständiger Unique Constraint

```sql
-- konzeptionell
UNIQUE (user_id, saved_product_profile_id, base_unit)
```

| Pro | Contra |
|-----|--------|
| Einfachste Semantik | **Scheitert**, sobald ≥2 aktive Core-Items denselben Schlüssel haben (heute durch Creation-Schleife **wahrscheinlich**) |
| Kein Zusatzfeld nötig | Blockiert Phase-2-Implementierung ohne vorherige Datenbereinigung |

**Bewertung:** Nur zulässig bei **garantiert konfliktfreien** Bestandsdaten — im Repository **nicht** als Startannahme.

#### Option B — Partieller Unique Index auf aktive kanonische Items ✅ **Empfohlen**

```sql
-- konzeptionell (Implementierung Phase 2)
CREATE UNIQUE INDEX … ON fertilizer_containers (user_id, saved_product_profile_id, base_unit)
WHERE access_kind = 'authenticated_user'
  AND saved_product_profile_id IS NOT NULL
  AND base_unit IS NOT NULL
  AND archived_at IS NULL
  AND stock_kind = 'product_stock';
```

| Pro | Contra |
|-----|--------|
| Legacy-Duplikate und Gebinde-Items **koexistieren** | Erfordert additive Spalte `stock_kind` |
| Phase 2 kann **sofort** neue kanonische Items schützen | Read-Seite muss Duplikate bis Phase 3 aggregieren/filtern |
| Archivierte Items ausgenommen | Zwei Semantiken auf einer Tabelle dokumentiert halten |

**Bewertung:** **Bevorzugt** — erfüllt Schutz neuer Schreibpfade ohne Phase-3-Vorarbeit.

#### Option C — Constraint erst nach Datenmigration (Phase 3)

| Pro | Contra |
|-----|--------|
| Kein Risiko durch Alt-Duplikate beim Constraint | **Kein** DB-Backstop für parallele Erst-Zugänge in Phase 2 |
| Einfacher Index nach Bereinigung | Race-Schutz nur über Anwendungslogik — **unzureichend** |

**Bewertung:** Als **alleinige** Phase-2-Strategie **verworfen**. Option C bleibt für **Verschärfung** nach Phase 3 (z. B. Entfernen `stock_kind`-Filter wenn nur noch kanonische aktive Zeilen existieren).

#### Empfehlung

**Option B** in Phase 2 implementieren. Option A erst prüfen, wenn Phase-3-Migrationsreport **null** Konflikte auf aktiven kanonischen Zeilen zeigt.

**Additive Spalte:**

| Spalte | Typ | Werte | Default |
|--------|-----|-------|---------|
| `stock_kind` | `text` CHECK | `product_stock`, `physical_package` | `NULL` (= historisches/legacy Item) |

Neue Intake-RPC setzt `stock_kind = 'product_stock'`, `package_size_* = NULL`.

**Voraussichtliche Constraint-Verletzer heute (Analyse, keine DB-Abfrage in diesem Schritt):**

- Mehrere `fertilizer_containers` mit gleichem `(user_id, saved_product_profile_id, base_unit)`, Core-gebunden, nicht archiviert — **erzeugt durch** `create_fertilizer_inventory_core_from_confirmed_packages`
- Legacy-Items ohne `saved_product_profile_id` — **nicht** im Partial Index
- Session-Items — separater Scope

### 25.6 Get-or-Create-Vertrag

**Fachlicher Ablauf** (serverseitig, eine Transaktion):

1. **Domain-Validierung** — spiegelt `validateFertilizerProductStockIntake` (Menge, Reason, IDs); Profil laden (`saved`, Form↔Unit).
2. **Kanonische Identität** — `(user_id, saved_product_profile_id, base_unit)`.
3. **Idempotenz-Receipt** — siehe §25.9; bei Replay → gespeichertes Ergebnis.
4. **Get-or-create Item:**
   - `INSERT INTO fertilizer_containers (…, stock_kind = 'product_stock')`
   - `ON CONFLICT` auf partiellem Unique **DO NOTHING**
   - `SELECT … FROM fertilizer_containers WHERE <Schlüssel> AND <aktiv-Kriterien> FOR UPDATE`
5. **Positive Movement** — über `append_fertilizer_inventory_core_movement` **oder** äquivalentes Inline-Insert mit denselben Checks (Saldo, Unit, Präzision, Immutability).
6. **Ergebnis** — `{ inventoryItemId, movementId, stockIdentity, quantityDelta, reason }` im Receipt persistieren.

**Regeln:**

- Ein Kauf erzeugt **kein** neues Item, wenn kanonisches Item existiert — nur Movement.
- Mehrere Käufe → mehrere Movements, **ein** Item.
- Kein clientseitiges „SELECT dann INSERT“ ohne DB-Schutz.

### 25.7 Race Conditions

| Szenario | Schutz |
|----------|--------|
| Zwei parallele **Erst**-Zugänge desselben Schlüssels | Partieller **Unique Index** + `INSERT … ON CONFLICT DO NOTHING` + anschließendes `SELECT … FOR UPDATE` |
| Parallele Zugänge auf **bestehendem** Item | `FOR UPDATE` auf Item-Zeile (bestehend in `append_*`) |
| Parallele **Idempotenz**-Retries | Receipt Unique + Advisory Lock (Muster Creation-RPC) + Movement Unique auf `inventory_idempotency_key` |
| Unique Violation nach Concurrent Insert | Catch → Re-SELECT Item → Movement append (Idempotenz-Key verhindert Doppel-Movement) |

**Warum clientseitiges Find-then-Insert nicht reicht:** Zwei Clients können beide „nicht gefunden“ lesen und zwei Items einfügen — nur ein **datenbankseitiger** Unique-Backstop verhindert das.

**Locks:** Keine manuelle Advisory-Lock-Pflicht für Get-or-Create **zusätzlich** zum Unique, sofern Transaktion + `FOR UPDATE` auf dem gefundenen Item. **Empfohlen:** Advisory Lock auf `(user_id, idempotency_key)` für Receipt-Serialisierung (bewährt in `create_fertilizer_inventory_core_from_confirmed_packages`).

| `created_at` | Insert-Zeitpunkt |
| `movement_date` | Abgeleitet aus `movement_at` (Legacy-Kompatibilität) |

### 25.9 Idempotenzvertrag

#### Schichten

| Ebene | Mechanismus | Scope |
|-------|-------------|-------|
| **Request / Operation** | Neue Tabelle `fertilizer_product_stock_intake_receipts` | `(user_id, idempotency_key)` authenticated |
| **Movement** | `inventory_idempotency_key` Unique (bestehend) | `(user_id, inventory_idempotency_key)` |
| **Payload-Integrität** | `payload_fingerprint` SHA-256 auf kanonischem JSON | pro Receipt |

#### Client-Key

- Vom Client, Conversation-Layer oder Command-Handler erzeugt
- **Nicht** nutzerübergreifend wiederverwendbar
- Empfohlenes Prefix: `product-stock-intake:` + opaque Token
- Max. Länge analog Creation (256)

#### Verhalten

| Fall | Ergebnis |
|------|----------|
| Gleicher Key + gleicher Payload (Fingerprint) | **Replay:** gespeichertes `result_jsonb` zurückgeben; **keine** zweite Movement |
| Gleicher Key + abweichender Payload | **Konflikt:** `INVENTORY_INTAKE_IDEMPOTENCY_CONFLICT` (maschinenlesbar) |
| Verschiedene Keys, gleicher Zugang | **Zwei** Movements (zwei bewusste Buchungen) |

#### Movement-Key-Ableitung

Deterministisch aus Receipt: z. B. `product-stock-intake:{receipt_id}` — verhindert Doppel-Insert innerhalb derselben Operation auch bei partieller Retry.

#### Einheitlicher Vertrag

Onboarding (`initial_stock`), Startseiten-Conversation und Ausrüstungs-Intake **müssen denselben RPC** und dieselbe Receipt-Semantik nutzen — keine UI-only-Idempotenz.

### 25.10 Transaktionsgrenze

**Atomare Einheit (eine PostgreSQL-Transaktion):**

1. Receipt anlegen oder sperren (`FOR UPDATE`)
2. Payload-Fingerprint prüfen
3. Get-or-create kanonisches Item
4. Idempotenz auf Movement-Ebene prüfen
5. Positive Movement einfügen
6. Receipt `result_jsonb` + `completed_at` setzen
7. Commit

**Empfehlung:** **Eine SECURITY DEFINER RPC** `record_fertilizer_product_stock_intake` — analog Creation-RPC, intern ggf. `append_fertilizer_inventory_core_movement` aufrufen.

| Mechanismus | Rolle |
|-------------|-------|
| RPC | Einziger Schreib-Einstieg für Produkt-Intake |
| Transaktion | Alles oder nichts |
| `ON CONFLICT` | Get-or-create Item |
| Partieller Unique | Race-Backstop |
| `FOR UPDATE` | Item-Zeile für Movement-Serialisierung |
| Advisory Lock | Receipt-Scope Serialisierung |
| **Kein** separater Client-Multi-Step | Verboten |

**Locks:** Row-Lock via `FOR UPDATE` ausreichend; **keine** zusätzliche manuelle Lock-Hierarchie ohne Messbedarf.

## 27. Phase 3 — Legacy-Migration bestehender Bestände (Spezifikation)

Dieser Abschnitt ist der **belastbare Migrationsvertrag** vor jeder schreibenden Datenmigration und vor der Read-Model-Umstellung (Phase 4). Er baut auf Phase 2 (`stock_kind`, Intake-RPC, partieller Unique Index) auf.

### 27.1 Ziel

Phase 3 behandelt **bestehende** Inventory Items **konservativ**, ohne historische Wahrheit zu verfälschen:

1. Legacy-Items **klassifizieren** (A–J)
2. Zukünftige **kanonische Produktbestände** pro Migrationsgruppe bestimmen
3. **Automatisch migrierbare** vs. **blockierte** Gruppen trennen
4. Für migrierbare Gruppen: kanonisches Ziel-Item vorbereiten oder wiederverwenden
5. Wirksamen Legacy-Saldo **einmalig und auditierbar** auf kanonisches Item übertragen
6. Legacy-Items **superseden/archivieren** — ohne Löschen, ohne Movement-Umhängen
7. Historische Application-/Journal-Referenzen **unverändert** lassen
8. Read Models (Phase 4) können danach **nur noch kanonische** aktive Bestände summieren
9. Jede Migration **idempotent, wiederholbar, prüfbar** (Dry Run → Schreiblauf)
10. **Datenverlust** und stille Zusammenführungen verhindern

**Nicht Ziel:** Sofortige UI-Umstellung, Legacy-RPC-Entfernung, Profilzusammenführung, Löschen alter Zeilen.

### 27.2 Ist-Risiken

| Risiko | Quelle (Repository) | Phase-3-Antwort |
|--------|---------------------|-----------------|
| Mehrere aktive Items pro `(user_id, profile, base_unit)` | Creation-Schleife `create_fertilizer_inventory_core_from_confirmed_packages` | Gruppierung + kanonisches Ziel |
| Legacy `stock_kind IS NULL` koexistiert mit `product_stock` | Phase-2-Migration | Klassifikation; Partial Index schützt nur `product_stock` |
| `append_fertilizer_inventory_core_movement` prüft **kein** `archived_at` | `20250805_fertilizer_inventory_core.sql` | Schreibschutz in Migrations-RPC + später Append-Erweiterung (§27.11) |
| Read-Liste summiert **alle** nicht archivierten Container | `fetchFertilizerStockList` | Phase 4: nur kanonische/superseded-filterte Summe |
| Movements ohne `movement_at` zählen nicht zum Core-Saldo | Balance-Core, Append-RPC | Explizit ausgeschlossen bei Saldoermittlung |
| Application-Batches FK → `inventory_item_id` | `20250808`/`20250809` | Historische IDs **nie** umschreiben |
| Parallele Alt- und Neu-RPC | K-7 §25.12 | Migration vor breitem Read-Switch; Schreibschutz auf superseded Legacy |
| Automatische Profilzusammenführung | DL-018 | **Verboten** |

### 27.3 Migrationsgruppe

**Definition (verbindlich):**

```text
(user_id, saved_product_profile_id, base_unit)
```

Gilt für `access_kind = 'authenticated_user'` mit gesetztem `saved_product_profile_id` und `base_unit`.

Eine Gruppe kann enthalten:

- genau ein Legacy-Item (`stock_kind IS NULL` oder `legacy_container`)
- mehrere Legacy-Items desselben Schlüssels
- bereits ein aktives `product_stock`-Item
- Legacy- und Product-Stock-Items **gemeinsam**
- archivierte Items (werden bei Klassifikation gesondert behandelt)
- Items ohne wirksame Movements
- widersprüchliche Daten (→ blockiert)

**Verboten als Gruppierungskriterium:**

| Kriterium | Warum verboten |
|-----------|----------------|
| Produktname / Hersteller / ähnliche Schreibweise | Kein Versionsanker ([DL-018](../decisions/dl-018.md)) |
| Package Size | Metadatum, keine Identität ([DL-028](../decisions/dl-028.md)) |
| NPK / Produktfamilie / Heuristik | Falsche Zusammenführung |
| Automatische Profilähnlichkeit | Zwei Saved Profiles = zwei Bestände |

**Session-Scope** (`access_kind = session`): **separater** Migrationspfad — nicht Teil des authenticated Produktbestands in Phase 3 v1.

### 27.4 Klassifikation A–J

| Klasse | Merkmale | Automatisch migrierbar? | Behandlung |
|--------|----------|-------------------------|------------|
| **A** | `stock_kind = 'product_stock'`, aktiv, Schlüssel eindeutig | Nein (bereits kanonisch) | Zielbestand; ggf. Legacy-Gruppe darauf migrieren (Klasse D) |
| **B** | Genau **ein** Legacy-Item; Saved Profile + Base Unit; Form/Unit konsistent; keine konkurrierenden kanonischen Items; wirksame Movements konsistent | **Ja** | Kanonisches Item anlegen/verwenden; bei Saldo > 0: **eine** `legacy_balance_migration`-Bewegung; Legacy supersede |
| **C** | Mehrere Legacy-Items; gleicher Nutzer/Profil/Base Unit; Form/Unit konsistent; Movement-Units konsistent | **Ja** | Ein kanonisches Ziel; **Summe** wirksamer Legacy-Salden → **eine** `legacy_balance_migration`-Bewegung; alle Legacy supersede |
| **D** | Aktives `product_stock`-Item **plus** Legacy-Items gleichen Schlüssels | **Ja** (mit Vorsicht) | Vorhandenes kanonisches Item = Ziel; Legacy-Saldo idempotent per `legacy_balance_migration` übernehmen |
| **E** | Fehlendes `saved_product_profile_id` oder Legacy ohne Core-Bindung | **Nein** | Bleibt Legacy; ggf. separater Pfad `fertilizerInventoryLegacyMigrationCore` / manuelle Profilzuordnung |
| **F** | Fehlende oder widersprüchliche `base_unit` | **Nein** | Keine kg↔ml-Umrechnung; Konfliktbericht |
| **G** | `product_form` widerspricht `base_unit` (Granulat≠kg, Flüssig≠ml) | **Nein** | Konfliktbericht; keine stille Korrektur |
| **H** | Widersprüchliche Movement-Daten (Units, ungültige Mengen, verwaiste Refs, negativer wirksamer Saldo) | **Nein** | Konfliktbericht; manuelle Klärung |
| **I** | Bereits archiviertes / fachlich abgeschlossenes Item | **Nein** (nicht reaktivieren) | Historisch erhalten; nur für Nachvollziehbarkeit |
| **J** | Wirksamer Saldo = 0; keine offene fachliche Relevanz | **Bedingt** | Supersede/Archivierung ohne Übernahmebewegung; **keine** leere kanonische Hülle nur „weil Duplikat existierte“ |

**Automatisch migrierbar:** B, C, D (nach Dry-Run-Validierung). **Blockiert:** E, F, G, H, I (Migration), J (nur Archivierung ohne Saldo).

### 27.5 Kanonisches Ziel-Item

**Ziel-Identität:** dieselbe wie Phase 2 — `(user_id, saved_product_profile_id, base_unit)` mit `stock_kind = 'product_stock'`, `archived_at IS NULL`, `access_kind = 'authenticated_user'`.

**Auswahlregel:**

1. Falls **aktives** `product_stock`-Item existiert → **dieses** Item (Klasse A/D)
2. Sonst: **neues** kanonisches Item via get-or-create (gleiches Muster wie Intake-RPC, **ohne** fachlichen Zugangsgrund zu simulieren — technische Anlage im Migrations-RPC)
3. **Niemals** zwei aktive kanonische Items pro Gruppe — Partial Unique Index ist Backstop

**Legacy-Items:** `stock_kind` **nicht** nachträglich auf `product_stock` setzen. Sie bleiben `NULL`/`legacy_container` bis archiviert.

### 27.6 Saldoübernahme

**Verbindlicher Vertrag:**

| Regel | Detail |
|-------|--------|
| Historische Movements | **Unverändert** am Legacy-`container_id` |
| Kanonisches Item | Erhält **keine** rückwirkend umgehängten Movements |
| Wirksamer Saldo | Summe `quantity_delta` WHERE `movement_at IS NOT NULL` pro Legacy-Item; Gruppensaldo = Summe über Legacy-Items der Gruppe |
| Übernahme | **Genau eine** positive `legacy_balance_migration`-Bewegung pro migrierter Gruppe mit Saldo > 0 ([DL-034](../decisions/dl-034.md)) |
| Audit | Mapping-Receipt verknüpft Gruppe, Legacy-IDs, Saldo, Stichtag, Übernahme-Movement-ID, Fingerprint |
| Idempotenz | Wiederholung liefert dasselbe Ergebnis — **keine** zweite Übernahme |
| `movement_at IS NULL` | **Nicht** in Saldo; ggf. separater Legacy-Upgrade-Pfad ([DL-028](../decisions/dl-028.md), K-5) — nicht still in Übernahme einrechnen |
| Nullsaldo | **Keine** Übernahmebewegung; nur Supersede/Archivierung |
| Negativer Saldo | **Keine** automatische Migration (Klasse H); manuelle Klärung |
| Stichtag | `migration_cutoff_at timestamptz` — Saldo zum Stichtag; Movements danach → Konflikt / erneute Analyse |
| Nachträgliche Legacy-Movements während Lauf | Migrations-RPC muss Gruppe sperren; nach Abschluss Legacy-Schreibschutz (§27.11) |

**Movement Reason — verbindlich entschieden (OD-M1 ✅):**

Der interne technische Movement Reason lautet **`legacy_balance_migration`** ([DL-034](../decisions/dl-034.md)).

| Aspekt | Vertrag |
|--------|---------|
| Bedeutung | Einmalige Übernahme eines geprüften **positiven** Legacy-Saldos auf kanonischen Produktbestand |
| Zulässig durch | Spätere Migrations-RPC / serverseitiger Migrationsprozess **nur** |
| Verboten | Onboarding, Startseite, Ausrüstung, normaler Intake-RPC, Append ohne Migrationskontext |
| Nicht verwenden | `initial_stock`, `purchase`, `gift_received`, `inventory_correction` — kein reales Ereignis, keine Korrektur |
| Mengenvertrag | Menge **> 0**; Base Unit = Gruppe; max. 4 Dezimalstellen; keine Rundung; keine kg↔ml |
| Nullsaldo | **Keine** `legacy_balance_migration`-Bewegung |
| Negativer Saldo | **Blockiert** — Klasse H; keine negative Übernahme |
| Receipt | **Zwingend** — isolierte Bewegung ohne Migration Receipt unzulässig |
| Persistenz | Enum/Constraint/RPC-Unterstützung folgen in Phase-3-**Implementierung**; Intake-RPC lehnt Reason weiterhin ab |
| Anzeige (später) | Sinngemäß „Übernommener früherer Bestand“ — Darstellungsvertrag only |

**Nutzer-Sichtbarkeit:** Übernahmebewegung **nicht** als Kauf/Düngung darstellen; Journal/Startseite ignorieren technische Migrationsbewegungen (Phase 4/6).

**Verworfen:** Korrektur-Paare auf Legacy-Items (früher §13-Entwurf); Read-Aggregation ohne Buchung als dauerhafte Lösung.

### 27.7 Keine historische Movement-Umschreibung

| Verbot | Begründung |
|--------|------------|
| `UPDATE fertilizer_stock_movements SET container_id = …` | Ledger immutable ([DL-019](../decisions/dl-019.md)); Trigger |
| DELETE Movements | Immutability |
| Neuberechnung historischer `quantity_delta` | Audit-Verlust |
| Umschreiben von `application_batch_id` / Journal-FKs | Historische Wahrheit |

Historische Detailansichten (Journal, Batch-Detail) zeigen weiterhin das **ursprüngliche** Item und dessen Movements.

### 27.8 Mapping-/Supersede-Strategie

#### Bewertete Optionen

| Option | Pro | Contra |
|--------|-----|--------|
| **A** — nur `archived_at` | Minimal | Keine Zielbeziehung; Doppelzählungsrisiko im Read Model; schwaches Audit |
| **B** — `archived_at` + `superseded_by_container_id` | Klare Zielkante; Read-Filter einfach | Kein Idempotenz-Receipt; unvollständiges Audit |
| **C** — Mapping-/Receipt-Tabelle ✅ | Idempotenz, Audit, Dry Run, Rollback-Grundlage; Muster Intake/Creation | Zusätzliche Tabelle |

#### Empfehlung ✅

**Option C + minimale Item-Spalte:**

1. **Neue Tabelle** `fertilizer_product_stock_migration_receipts` (Arbeitstitel) — Request-/Gruppen-Idempotenz, analog Intake-Receipts
2. **Additive Spalte** `superseded_by_container_id uuid NULL` auf `fertilizer_containers` — FK → kanonisches Item, **keine** Zyklen (CHECK `id <> superseded_by_container_id`)
3. **`archived_at`** auf superseded Legacy-Items setzen
4. **`archive_reason`** optional text CHECK — z. B. `product_stock_migration_superseded`

**Mapping-Tabelle — Mindestfelder:**

| Feld | Zweck |
|------|-------|
| `id` (PK) | Receipt-/Operations-ID |
| `user_id` | Owner |
| `migration_group_key` | Deterministischer Schlüssel (Hash aus user + profile + base_unit + Stichtag-Policy) |
| `idempotency_key` | Client-/Job-Key; UNIQUE `(user_id, idempotency_key)` |
| `payload_fingerprint` | SHA-256 kanonisches JSON |
| `saved_product_profile_id`, `base_unit` | Gruppe |
| `legacy_container_ids` | jsonb/array — sortierte UUIDs |
| `canonical_container_id` | Ziel-Item |
| `takeover_movement_id` | NULL wenn Saldo 0; sonst FK → Movement mit `movement_type = 'legacy_balance_migration'` |
| `effective_balance` | Übernommener Saldo (4 Dezimalstellen) |
| `migration_cutoff_at` | Stichtag |
| `status` | `pending` / `completed` / `conflict` |
| `result_jsonb` | Replay-Ergebnis |
| `created_at`, `completed_at` | Audit |

RLS: wie Intake-Receipts — **kein** direkter Client-Schreibzugriff.

**`archived_at` allein reicht nicht** — immer in Kombination mit Mapping-Receipt und `superseded_by_container_id`.

### 27.9 Idempotenz und Fingerprint

**Schichten:**

| Ebene | Mechanismus |
|-------|-------------|
| Gruppen-Receipt | `(user_id, idempotency_key)` UNIQUE |
| Movement | `(user_id, inventory_idempotency_key)` — Key deterministisch aus Receipt-ID, z. B. `product-stock-migration:{receipt_id}`; Reason **`legacy_balance_migration`** |
| Advisory Lock | `(user_id, migration_group_key)` — Serialisierung paralleler Läufe |

**Fingerprint-Kanon (SHA-256), mindestens:**

- `userId`
- `savedProductProfileId`
- `baseUnit`
- `legacyContainerIds` (sortiert, stabil)
- `effectiveMovementIds` oder reproduzierbare Movement-Checksum (nur wirksame Movements mit `movement_at`)
- `migrationCutoffAt`
- `computedBalance` (formatiert, 4 Dezimalstellen)
- `movementReason`: `'legacy_balance_migration'` (konstant)
- `canonicalContainerId` (falls bereits vorhanden)

**Verhalten:**

| Fall | Ergebnis |
|------|----------|
| Gleicher Auftrag + unveränderte Quelle | **Replay:** gespeichertes `result_jsonb`; keine zweite Übernahme |
| Gleicher Key + veränderte Quelle | **Konflikt:** `PRODUCT_STOCK_MIGRATION_IDEMPOTENCY_CONFLICT`; erneute Analyse |
| Neue Legacy-Movements nach abgeschlossener Migration | **Kein** Auto-Nachziehen; separates Ereignis oder manueller Re-Run mit neuem Key |

### 27.10 Transaktionsgrenze (atomarer Ablauf)

Pro Migrationsgruppe — **eine PostgreSQL-Transaktion:**

1. Nutzer + Gruppe validieren; Klasse B/C/D bestätigen
2. Advisory Lock + Receipt anlegen oder `FOR UPDATE` auf bestehendem Receipt
3. Fingerprint prüfen
4. Legacy-Items erneut laden; Saldo zum Stichtag berechnen
5. Kanonisches Item finden oder anlegen (`stock_kind = 'product_stock'`)
6. Prüfen: Gruppe bereits `completed` → Replay
7. Falls Saldo > 0: **genau eine** `legacy_balance_migration`-Bewegung auf kanonischem Item
8. Mapping-Receipt `completed`; Legacy-Items: `superseded_by_container_id`, `archived_at`
9. Commit

**Bei Fehler:** vollständiger Rollback — keine archivierten Items ohne Receipt, keine Übernahme ohne Mapping.

### 27.11 Schreibschutz alter Pfade

**Ist-Analyse (Repository):**

| Pfad | Schreibt Legacy? | `archived_at`-Check? |
|------|------------------|----------------------|
| `create_fertilizer_inventory_core_from_confirmed_packages` | Ja — neue Legacy-Items (`stock_kind` NULL) | Nein |
| `record_fertilizer_product_stock_intake` | Nein — nur `product_stock`; lehnt `legacy_balance_migration` ab | — |
| `append_fertilizer_inventory_core_movement` | Ja — beliebiges Item | **Nein** (Stand `20250805`) |
| `apply_fertilizer_inventory_item_to_areas` | Indirekt — negative Movement | Item-Eligibility; kein Supersede-Check |

**Anforderungen vor produktiver Migration:**

1. Migrierte Legacy-Items (`superseded_by_container_id IS NOT NULL` oder Mapping `completed`) dürfen **keine** neuen Movements erhalten
2. Append-RPC (oder Wrapper) muss superseded/archivierte Items **ablehnen** — Implementierung Phase 3/6
3. Creation-RPC darf **keine** neuen Duplikat-Gruppen erzeugen, sobald kanonischer Bestand existiert — Routing Phase 6
4. Application-RPC darf weiter historische Item-IDs lesen; neue Düngungen nur auf **kanonische** Items (Phase 5)

**Reihenfolge:**

```
Dry Run → Schreibmigration Gruppe für Gruppe → Legacy-Schreibschutz aktiv → Read Model Phase 4
```

Ohne Schreibschutz: **kein** breiter Read-Switch.

### 27.14 Teststrategie (Implementierung)

#### Klassifikation

- Jede Klasse A–J mit Fixtures
- Unterschiedliche Saved Profiles → **nie** eine Gruppe
- Package Size / Produktname → **kein** Einfluss auf Gruppierung

#### Saldo

- Nur `movement_at IS NOT NULL`
- Positive, null, negative Salden
- 4 Dezimalstellen; keine Rundung; keine kg↔ml

#### Migration

- Einzelnes Legacy; mehrere Legacy; vorhandenes kanonisches Item
- Genau **eine** `legacy_balance_migration`-Bewegung bei Saldo > 0; **keine** bei Nullsaldo
- Negativer Saldo → Migration blockiert
- Mapping vollständig; Receipt-Verknüpfung zwingend
- Legacy superseded; historische Movements unverändert (byte-identisch)
- Application-Batch-/Journal-FKs unverändert

#### Idempotenz

- Wiederholung → Replay; **keine** zweite `legacy_balance_migration`; veränderte Quelle → Konflikt; Teilfehler → Rollback

#### Concurrency

- Zwei parallele Migrationsversuche → eine erfolgreich; kein Doppel-Movement

#### Legacy-Schreibschutz

- Superseded Item → Append abgelehnt; kanonisches Item weiter beschreibbar

#### Security

- Nur eigene Gruppen; kein fremdes Item/Movement/Receipt

- Gleicher Key + gleiche Payload → Replay desselben Batches und derselben Movement
- Gleicher Key + andere Payload → Konflikt
- Produktauswahl und Navigation sind **nicht** idempotent persistiert — nur der Submit
