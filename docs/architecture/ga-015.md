## 2. Ausgangslage

Greenkeeper implementiert Düngerbestand heute als **Gebinde-Modell**:

| Ebene | Ist-Stand (Repository `bc49546` / `e14522d`) |
|-------|-----------------------------------------------|
| **Tabelle Inventory Item** | `public.fertilizer_containers` — Kommentar/Migration: „physisches Gebinde“ |
| **Tabelle Movement** | `public.fertilizer_stock_movements` — append-only, `movement_at` kanonisch |
| **Creation** | `create_fertilizer_inventory_core_from_confirmed_packages` — **ein Item pro Packung** in Schleife |
| **Zugang** | Initiale positive Movement pro neuem Item (`initial_stock`, `purchase`, `gift_received`) |
| **Bestandsliste** | Client: `fetchFertilizerStockList` — **ein Listeneintrag pro Container**, Saldo je Item |
| **Düngung** | Route `/ausruestung/duenger/:inventoryItemId/anwenden`, RPC `apply_fertilizer_inventory_item_to_areas` |
| **Constraint Düngung** | Unique Index `fertilizer_stock_movements_application_batch_idx` — **genau ein Movement pro Batch** (kompatibel mit DL-033) |
| **Unique Produktbestand** | **Kein** Unique Constraint auf `(user_id, saved_product_profile_id, base_unit)` — nur Indizes |

[DL-033](../decisions/dl-033.md) definiert das **Zielbild Version 1**: ein Inventory Item = **Produktbestand**, kein Gebinde, keine FIFO, Startseite als Tätigkeitseinstieg.

## 3. Zielvertrag (DL-033, technisch)

| Regel | Ziel |
|-------|------|
| Inventory Item | Ein **kompatibler mengenmäßiger Produktbestand** pro Schlüssel |
| Gebinde | **Nicht** modelliert; Packungsgröße nur Zugangsmengen-Eingabe |
| Zugang | Positive Movement auf **bestehendem oder neu angelegtem** Produktbestand |
| Düngung | **Genau eine** negative Movement; **ein** Batch; Mehrflächen unverändert |
| Bestand | Summe Movements mit `movement_at IS NOT NULL`; **kein** `currentQuantity` |
| FIFO / Gebindestatus | **Nicht** in Version 1 |
| Startseite | Primärer Einstieg „Düngung erfassen“ |
| Ausrüstung | Bestand/Nachschlage; **kein** primärer „Anwenden“-Button |
| Parallele Logik | **Verboten** — ein Flow, ein RPC |

## 4. Ist-Architektur (Detail)

### 4.1 Datenmodell

**`fertilizer_containers` (Inventory Item)**

- PK `id`; `user_id`; `saved_product_profile_id` (FK `product_profiles`, `profile_status = saved`)
- `access_kind` (`authenticated_user` | `session`); `base_unit` (`kg` | `ml`)
- `package_size_value` / `package_size_unit` — nominale Packung
- Legacy: `product_id`, `recognition_candidate_id`, `label`
- Kein `product_form` auf Container — Form über Join `product_profiles.product_form`
- Keine Spalte `product_version_id`
- Saldo: abgeleitet aus Movements

**`fertilizer_stock_movements`**

- `container_id` → Item; `quantity_delta`; `unit`; `movement_type`; `movement_origin`
- `movement_at` — kanonisch für Saldo
- `application_batch_id` — FK zu `fertilizer_application_batches` (unique wenn gesetzt)
- Immutability: Trigger `prevent_fertilizer_stock_movement_update/delete`

**Application / Journal**

- `fertilizer_application_batches` — 1 pro Düngung; `inventory_item_id`, Idempotenz
- `fertilizer_application_areas` — je Fläche
- `activities` + `fertilization_details` — je Fläche; Snapshots
- RPC: `apply_fertilizer_inventory_item_to_areas(p_inventory_item_id, p_saved_product_profile_id, …)`

**Saved Product Profile**

- `product_profiles.profile_status = 'saved'` — **immutable** (Trigger `prevent_saved_product_profile_mutation`)
- Repräsentiert konkrete Produktversion ([DL-018](../decisions/dl-018.md))
- `product_form` (`granular` | `liquid`) auf Profil

### 4.2 Erstellung und Zugang

- **RPC:** `create_fertilizer_inventory_core_from_confirmed_packages(p_saved_product_profile_id, packages[], reason, …)`
- Schleife: **pro Packung** INSERT Container + INSERT initiale positive Movement
- Receipt/Idempotenz: `fertilizer_inventory_creation_receipts`
- Client: `fertilizerInventoryCreation*.ts`, Capture-Integration

### 4.3 Bestandsanzeige

- `fetchFertilizerStockList()` — lädt alle Container, berechnet Saldo je Item
- `FertilizerCategoryPage` — Listeneintrag je Item, Text „Gebinde …“, Link **„Anwenden“**
- Keine serverseitige Aggregation nach Produktbestandsschlüssel

### 4.4 Düngung

- `FertilizerApplicationPage` — `useParams().inventoryItemId` Pflicht
- Flow-Core: `fertilizerApplicationFlowCore.ts`, Multi-Area: `fertilizerMultiAreaApplication*.ts`
- Submit: `applyFertilizerInventoryItemToAreas` → RPC mit `p_inventory_item_id`
- Eligibility: Core-gebundenes Item (`saved_product_profile_id`, `access_kind`, `base_unit`)

### 4.5 Startseite

- `HomeScreen`, `HomeVoiceSection` — Sprache/Text dokumentiert ([home-experience](../playbook/home-experience.md))
- **Kein** dedizierter CTA „Düngung erfassen“ mit Produktauswahl
- `homeVoiceFlow.ts` — Intent-Struktur vorhanden, Düngung noch nicht an Mehrflächen-RPC angebunden

## 6. Produktbestandsschlüssel

### 6.1 Fachlicher Schlüssel (DL-033)

```
(user_id, saved_product_profile_id, form, base_unit)
```

### 6.2 Persistierte Felder (Ist)

| Komponente | Persistenz | Quelle |
|------------|------------|--------|
| `user_id` | ✅ | `fertilizer_containers.user_id` |
| `saved_product_profile_id` | ✅ | `fertilizer_containers.saved_product_profile_id` |
| `form` | ⚠️ indirekt | `product_profiles.product_form` (immutable wenn `saved`) |
| `base_unit` | ✅ | `fertilizer_containers.base_unit` |

**Keine** Spalte `product_version_id`. **Keine** neue Spalte in Phase 1 erfinden, sofern Gate A grün.

### 6.3 Empfehlung Unique Constraint (Gate A)

```sql
-- Konzeptionell (Umsetzung Phase 2):
UNIQUE (user_id, saved_product_profile_id, base_unit)
WHERE access_kind = 'authenticated_user'
  AND saved_product_profile_id IS NOT NULL
  AND archived_at IS NULL
  AND stock_kind = 'product_stock'  -- optional, siehe Migration
```

**Begründung:** `saved_product_profile_id` bindet **immutable** an genau eine `product_form` ([DL-018](../decisions/dl-018.md), Trigger auf `saved`). `base_unit` ist redundant zu Form nur insofern, als DB bereits `granular→kg`, `liquid→ml` erzwingt — **beide** im Schlüssel dokumentieren, Unique technisch auf `(user_id, saved_product_profile_id, base_unit)`.

**Session-Scope** (`access_kind = session`): separater Schlüssel mit `session_access_hash` — nicht Teil des authenticated Produktbestands.

## 7. Versionsanker

### Ist-Stand

- **`saved_product_profile_id`** verweist auf `product_profiles` mit `profile_status = 'saved'`
- Saved Profiles sind **unveränderlich** (`prevent_saved_product_profile_mutation`)
- Neue Herstellerdeklaration → **neues** Saved Profile ([DL-018](../decisions/dl-018.md)) — **keine** Zusammenführung

### Beantwortung Gate A

| Frage | Antwort |
|-------|---------|
| Reicht `saved_product_profile_id` als Produkt- **und** Versionsanker? | **Ja**, für v1 — Saved Profile = konkrete unveränderliche Produktversion |
| Kann Saved Profile später verändert werden? | **Nein** (DB-Trigger) |
| Braucht es `product_version_id`? | **Nein** in v1 — offene Ergänzung nur falls später explizite Versionstabelle eingeführt wird |

### Offene Frage (Gate A, dokumentiert)

Ob **zwei** Saved Profiles fachlich „dasselbe Produkt“ sein können, ohne dass der Nutzer es erkennt — dann entstehen **zwei** Produktbestände (**korrekt** nach DL-018/DL-033). Keine automatische Merge-Heuristik.

## 8. Zielarchitektur

### 8.1 Produktbestand

```
Produktbestand (1 × fertilizer_containers-Zeile pro Schlüssel)
  └── Movements (append-only, movement_at gesetzt)
        ├── + initial_stock | purchase | gift_received
        └── − fertilization (journal)
```

- Kein `currentQuantity`
- Keine Gebindeobjekte, kein FIFO
- `package_size_*` optional, nur Capture-Hilfe

### 8.2 Zugang

```
find_or_create_product_stock(user, saved_product_profile_id, base_unit)
  → atomar: SELECT … FOR UPDATE | INSERT
  → append_positive_movement(amount, reason)
```

- Idempotenz über Receipt + Movement-Key (bestehendes Muster)
- Race: Unique Constraint + Retry auf Unique Violation → Re-SELECT

### 8.3 Anwendung

```
Startseite → Produktbestand wählen → Flächen/Modus/Menge → Bestätigung
  → apply_fertilizer_inventory_item_to_areas(p_inventory_item_id = kanonische Item-ID, …)
  → 1 Batch, N Activities, 1 negative Movement
```

- **RPC-Semantik unverändert** — nur Einstieg und Item-Auflösung ändern sich
- `p_inventory_item_id` bleibt — Wert = **Produktbestands-Item**

### 8.4 Ausrüstung

- Read-only Liste: Produktname, Saldo, Base Unit
- Kein „Anwenden“; optional Produkt-/Profil-Detail
- Capture/Erfassung bleibt separater Zugang (Phase 6)

### 8.5 Journal

- Unverändert: je Area Activity; Snapshots; keine sichtbare Bestandskomplexität

**Ablauf:**

2. Produktbestand find-or-create (Unique + Lock)

4. Receipt speichern

**Packungsgröße:** nur Request-Metadatum für UI; **nicht** auf Item persistieren als Identität (optional weiter als nullable Metadatum der **Movement**-Notiz).

## 13. Datenmigration (Strategie)

### Prinzipien

- **Additiv zuerst** — keine destruktive Löschung von Movements
- **Ledger unveränderlich** — kein UPDATE auf `fertilizer_stock_movements`
- **Historische FKs** — `fertilization_details.inventory_item_id`, `application_batches.inventory_item_id` **nicht** umschreiben
- **Rollback** — Migrationsschritte idempotent + reversibel wo möglich (Archivierung statt DELETE)

### Duplikat-Gruppen (mehrere kompatible Container)

**Erkennung:** Gleicher `(user_id, saved_product_profile_id, base_unit)`, Core-gebunden, nicht archiviert.

**Kanonisches Item wählen** (deterministisch):

1. Höchster Saldo > 0
2. Sonst ältestes `created_at`
3. Tie-Breaker: `lower(id::text)`

**Superseded Items:**

- Spalte `superseded_by_container_id uuid` (additiv) **oder** `archived_at` + `archive_reason = 'superseded_by_product_stock_migration'`
- Movements **bleiben** am Original-Container

**Saldo-Konsolidierung (empfohlen, Gate B):**

- Pro superseded Item mit Saldo ≠ 0: **Paar** von Movements in **einer** Migrationstransaktion:
  - `inventory_correction` −Saldo auf superseded Item
  - `purchase` oder `migration` +Saldo auf kanonischem Item
- **Summe global unverändert**; Ledger append-only
- Alternativ (konservativer Übergang): Read-Aggregation ohne Buchung bis Saldo natürlich verbraucht — **langsamer**, weniger Risiko

**Application-eligible nach Migration:** nur kanonische Items; superseded archiviert.

### Legacy ohne Core-Bindung

- Nicht application-eligible (bestehend)
- Nicht in Produktbestandsliste
- Separater Migrations-/Upgrade-Pfad ([DL-030](../decisions/dl-030.md))

### Verbrauchte Alt-Items (Saldo 0)

- Archivieren; kein Merge nötig

### Inkompatible Items

- Nicht zusammenführen; bleiben einzeln bis manuelle Klärung

## 15. Idempotenz

- **Zugang:** Receipt-Tabelle analog `fertilizer_inventory_creation_receipts`; Fingerprint inkl. `saved_product_profile_id`, `quantity`, `reason`, `idempotency_key`
- **Düngung:** unverändert `fertilizer_application_batches` + `request_fingerprint`
- **Migration:** Migrations-Receipt oder `migration_batch_id` pro konsolidiertem Item-Paar — Wiederholung safe

---

## 16. Konkurrenz und Locks

| Vorgang | Mechanismus |
|---------|-------------|
| Parallele Zugänge | `SELECT … FOR UPDATE` auf kanonischem Item **oder** Advisory Lock auf `(user_id, profile_id, base_unit)`; Unique als Backstop |
| Parallele Düngungen | Bestehend: Item-Lock im RPC + Saldo-Reprüfung |
| Migration | Batch-weise; keine User-Writes während Item-Konsolidierung pro Gruppe (Maintenance-Flag optional) |

## 17. Teststrategie

### Domain (Phase 1)

- Gleicher Schlüssel; inkompatible Form/Unit/Profil
- Positiver/negativer Saldo; Präzision; unzureichender Bestand
- Find-or-create Semantik

### Persistenz (Phase 2)

- Erster Zugang erstellt Item; zweiter nutzt dasselbe
- Parallele Zugänge → kein Duplikat
- Idempotenz Replay/Konflikt
- Düngung: genau 1 Movement; Rollback; RLS; Immutability

### Migration (Phase 3)

- 1 / N kompatible Alt-Items; historische Anwendungen; verbraucht; Legacy; inkompatibel
- Movement-Summen invariant; wiederholbare Migration

### UI (Phase 4–5)

- Ausrüstung ohne Apply; Produktbestand sichtbar
- Startseiten-CTA; Ein-/Mehrflächen; Pflegegruppe; Fehler erhält Eingaben
- Kein Gebindetext

### Clean-HEAD

- Jede Phase committbar unabhängig vom lokalen WIP
- Dev-DB-Tests nur mit Opt-in ([GA-010](./ga-010.md))
