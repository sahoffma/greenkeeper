## Kontext

Vor der Mehrflächen-Persistenzmigration ([DL-031](./dl-031.md)) muss der dauerhafte Löschvertrag für Flächen feststehen. Produktseitig gelten Flächen als eigenständige fachliche Objekte; gemeinsame Pflege, Pflegegruppen und Mehrflächenanwendungen verbinden Flächen **nicht** deren Lebenszyklus.

Der Ist-Zustand (Stand `origin/main` + unveröffentlichte Fertilizer-Commits):

- `deleteArea` in `src/lib/areas.ts` führt einen direkten `DELETE` auf `areas` aus — kein Soft Delete über `archived_at`.
- `areas.archived_at` existiert, wird beim Löschen aber **nicht** gesetzt; Abfragen filtern aktive Flächen mit `archived_at IS NULL`.
- Flächen mit inventory-gekoppelten Düngeranwendungen ([DL-030](./dl-030.md)) sind heute **nicht** löschbar: `fertilizer_application_receipts.area_id ON DELETE RESTRICT`, `activity_id ON DELETE RESTRICT` sowie Immutability-Trigger auf inventory-gekoppelten `activities` / `fertilization_details`.
- Pflegegruppen: `care_group_areas.area_id ON DELETE CASCADE` entfernt die Mitgliedschaft; Trigger `care_group_areas_prune` löst `prune_care_groups` aus und entfernt Gruppen mit weniger als zwei Mitgliedern ([DL-008](./dl-008.md)).

Dieser Decision Log legt den **Zielvertrag** fest und beschreibt die **späteren SQL-Anpassungen** — ohne sie in diesem Block umzusetzen.

---

## Entscheidung

### Nutzervertrag

Die Nutzeraktion heißt weiterhin **„Fläche löschen“**.

Vor Bestätigung muss die UI später klar erklären (Umsetzung **nicht** in diesem Block):

- Die Fläche wird **dauerhaft** entfernt.
- Ihre zugehörigen Journaleinträge werden **dauerhaft gelöscht**.
- Andere Flächen und deren Journaleinträge bleiben erhalten.
- Bereits verbuchte Bestandsverbräuche bleiben bestehen — **kein Rückbuchen**.
- Die Aktion ist **nicht rückgängig** zu machen, sofern kein separater Wiederherstellungsvertrag existiert.

Es wird **standardmäßig kein dauerhaft sichtbares Archiv** ehemaliger Flächen aufgebaut.

### Interner Vertrag — Löschdomäne

| Domäne | Löschbar einzeln? |
|--------|-------------------|
| **Area** | ✅ Ja — einzige Löschdomäne dieses Vertrags |
| **Care Group** | ❌ Nein — keine Kaskade beim Flächenlöschen |
| **Mehrflächenanwendung / Batch** | ❌ Nein — kein Löschen wegen einer beteiligten Fläche |
| **Inventory Movement** | ❌ Nein — append-only Ledger ([DL-019](./dl-019.md)) |

Regeln:

1. Das Löschen einer Fläche darf **niemals** eine andere Fläche löschen, archivieren oder fachlich verändern.
2. Batch- und Care-Group-Zugehörigkeit begründen **keine Kaskade** auf andere Areas.
3. Gelöschte Flächen erscheinen nicht mehr in aktiven Flächenauswahlen, Pflegeansichten oder Düngeranwendungen.

### Beim Löschen genau einer Fläche werden entfernt

| Daten | Aktion |
|-------|--------|
| `areas`-Zeile der Fläche | `DELETE` |
| `care_group_areas`-Mitgliedschaft | `DELETE` (FK `ON DELETE CASCADE`) |
| Eigene `activities` | `DELETE` |
| Eigene `fertilization_details` | `DELETE` (via Activity-Cascade) |
| Eigene `measure_details` | `DELETE` (via Activity-Cascade) |
| Flächenbezogene Dashboard-/Planungsdaten (`area_health_scores`, `daily_briefings`, `nutrient_budgets`) | `DELETE` (FK `ON DELETE CASCADE`) |
| Flächenbezogene Zuordnung in Mehrflächenanwendungen (`fertilizer_application_areas`) | `DELETE` (Modell A — siehe unten) |
| Storage-Objekt für `cover_image_path` | Später im `delete_area`-RPC entfernen, falls gesetzt |

### Bleiben erhalten

| Daten | Regel |
|-------|-------|
| Alle anderen `areas` | unverändert |
| Activities / Details **anderer** Flächen | unverändert |
| Care-Group-Mitgliedschaften **anderer** Flächen | unverändert |
| Gemeinsamer Application-**Batch** | unverändert, solange Movement oder andere Flächenbezüge existieren |
| Gemeinsames **Inventory Movement** | unverändert in voller Höhe; kein Rückbuchen |
| Historischer Bestandsverbrauch | unverändert |
| Minimale Batch-/Receipt-Metadaten | für Idempotenz und Bestandsnachvollziehbarkeit |
| Unveränderliche Movement-Historie | append-only |

### Ausnahme zur DL-030-Journal-Unveränderlichkeit

[DL-030](./dl-030.md) verbietet das Löschen inventory-gekoppelter Journal-Einträge im Normalfall.

**Explizite Ausnahme:** Beim **Flächenlöschen** dürfen die **eigenen** inventory-gekoppelten `activities` und `fertilization_details` der gelöschten Fläche entfernt werden.

**Nicht** ausgenommen:

- `fertilizer_stock_movements` — bleiben append-only
- Journal-Einträge **anderer** Flächen — bleiben unveränderlich
- nachträgliche Mutation von Batch-Gesamtmenge, Fingerprint oder Movement-Menge

Die spätere Implementierung muss diese Ausnahme **ohne** Trigger-Deaktivierung, **ohne** `session_replication_role` und **ohne** Superuser-Annahme umsetzen — über `areas`-Trigger `set_area_deletion_context` (setzt `greenkeeper.area_deletion_id`) und angepasste Immutability-Trigger, die DELETE nur bei passendem Löschkontext erlauben (Migration `20250809_fertilizer_multi_area_application_atomic.sql`).

## Mehrflächenanwendung nach Flächenlöschung

### Beispiel (Produktinhaber)

**Ausgangslage:**

- Fläche 1 und Fläche 2 in derselben Pflegegruppe.
- Gemeinsam 3 kg gedüngt; Fläche 1: 2 kg, Fläche 2: 1 kg.
- Ein Movement `-3 kg`, zwei Activities, zwei Details, ein Batch, zwei Batch-Area-Zuordnungen.

**Nach Löschen von Fläche 1:**

| Objekt | Zustand |
|--------|---------|
| Fläche 1 | existiert nicht mehr |
| Care-Group-Zuordnung Fläche 1 | entfernt |
| Activity / Detail Fläche 1 | entfernt |
| Batch-Area-Zuordnung Fläche 1 | entfernt |
| Fläche 2, deren Activity, Detail, Batch-Zuordnung, Care-Group-Mitgliedschaft | **unverändert erhalten** |
| Movement | **`-3 kg` unverändert** |
| Inventory-Saldo | **unverändert** — kein Rückbuchen |
| Batch-Gesamtmenge / Fingerprint | **unverändert** — nicht auf 1 kg reduziert |
| Aktive Journalansicht Fläche 2 | zeigt nur den Eintrag von Fläche 2 |

Eine gemeinsame Anwendung wird nach Löschen einer beteiligten Fläche zu einer **historisch teilweise reduzierten Journalansicht**. Verbleibende Area-Einträge behalten ihre ursprünglichen Mengen, Raten und Snapshots.

Eine spätere Bestandsansicht darf den Verbrauch als gemeinsame Anwendung mit teilweise gelöschtem Flächenbezug kennzeichnen — UI nicht in diesem Block.

## Batch-Vertrag

1. Der Batch ist **nicht Eigentum** einer einzelnen Area.
2. Der Batch wird beim Löschen einer Area **nicht** gelöscht, solange ein Movement darauf verweist, andere Batch-Area-Zuordnungen existieren oder er als Bestands-/Idempotenznachweis benötigt wird.
3. `fertilizer_application_batches.inventory_item_id` bleibt `ON DELETE RESTRICT`.
4. `fertilizer_application_batches.movement_id` darf durch Area-Löschung **nicht** verändert werden.
5. Batch-Gesamtmenge, Fingerprint und bestätigter Gesamtwert bleiben **unverändert**.
6. Keine rückwirkende fachliche Umschreibung des Batch-Resultats.
7. Optional darf der Batch erkennen lassen, dass einzelne Flächenbezüge später gelöscht wurden — **ohne** Mutation des ursprünglichen Payloads (z. B. fehlende aktive `fertilizer_application_areas`-Zeilen statt Tombstone-Entität).

**Bevorzugte Lösung:** Flächenbezogene Journalzuordnung wird gelöscht; Batch und Movement bleiben; keine dauerhafte „ehemalige Fläche“-Entität; keine Neuberechnung.

**Nachvollziehbarkeitslücke (bewusst akzeptiert):** Nach Löschung **aller** beteiligten Flächen ist die ursprüngliche Teilmengenverteilung im Journal nicht mehr lesbar. Für die **Bestandsintegrität** reicht der Batch-Gesamtvertrag (Gesamtentnahme, Produkt, Zeitpunkt, Movement, Idempotenzschlüssel). Eine spätere Inventory-UI kann optional darauf hinweisen, dass zugehörige Flächen entfernt wurden.

## Modell für `fertilizer_application_areas` (Folge-Migration)

### Modell A — Zuordnung wird mit Activity gelöscht ✅ Empfohlen

- `activity_id NOT NULL`, `ON DELETE CASCADE`
- `area_id NOT NULL`, `ON DELETE CASCADE`
- Beim Löschen der Area: Zuordnungszeile verschwindet mit Activity-Cascade bzw. Area-Cascade
- Andere Zuordnungen bleiben

### Modell B — Tombstone-Zuordnung

- `activity_id ON DELETE SET NULL`, `area_id ON DELETE SET NULL`
- Snapshots bleiben als historische Zeilen erhalten
- Widerspricht Datenminimierung und Nutzererwartung „dauerhaft löschen“

**Empfehlung: Modell A** — passt zu Produktpräferenz (keine unnötige dauerhafte Fläche im Hintergrund), DL-031-Snapshots auf Activity-Ebene für verbleibende Flächen, und Bestandsnachvollziehbarkeit über Batch + Movement.

## FK-Vertrag für die spätere Migration

Ohne SQL in diesem Block; exakte Vorgaben für den Mehrflächen-Migrationsblock:

| FK | Regel | Wirkung |
|----|-------|---------|
| `activities.area_id` | `NOT NULL`, `ON DELETE CASCADE` | **Beibehalten** — Area-Löschung löscht nur eigene Activities |
| `fertilization_details.activity_id` | `ON DELETE CASCADE` | **Beibehalten** |
| `measure_details.activity_id` | `ON DELETE CASCADE` | **Beibehalten** |
| `fertilizer_stock_movements.activity_id` | `NULL`, `ON DELETE SET NULL` | **Bereits so** — Movement bleibt, Referenz wird null |
| `fertilizer_application_batches` | keine Area-FK | Batch unabhängig von einzelner Fläche |
| `fertilizer_application_batches.movement_id` | `NOT NULL`, `ON DELETE RESTRICT` | Movement nicht über Batch löschbar |
| `fertilizer_application_batches.inventory_item_id` | `ON DELETE RESTRICT` | **Beibehalten** |
| `fertilizer_application_areas.area_id` | `NOT NULL`, `ON DELETE CASCADE` | Modell A |
| `fertilizer_application_areas.activity_id` | `NOT NULL`, `ON DELETE CASCADE` | Modell A |
| `fertilizer_application_areas.application_batch_id` | `ON DELETE RESTRICT` | Batch nicht durch Area-Löschung entfernen |
| `care_group_areas.area_id` | `ON DELETE CASCADE` | **Beibehalten** — nur Membership der gelöschten Fläche |
| `fertilizer_application_receipts.area_id` (DL-030 Einzelfläche) | später `ON DELETE SET NULL` oder RPC-Löschung vor Area-Delete | Receipt ist technischer Idempotenznachweis, nicht Inventory-Wahrheit |

### Primary Activity und Movement

- Das Movement verweist primär auf den **Batch** (`application_batch_id`), nicht auf eine einzelne Fläche.
- `activity_id` auf dem Movement zeigt optional auf die **Primary Activity** (niedrigste `sort_order` / kanonisch erste `area_id`).
- Wird die Primary Activity gelöscht (Area-Löschung): `activity_id` → `NULL` via `ON DELETE SET NULL`; Movement bleibt dem Batch zugeordnet.
- Primary Activity bleibt **sinnvoll** als optionale Hilfsreferenz — fachliche Zuordnung erfolgt über `application_batch_id`.

### Verhalten bei Löschen aller Areas eines Batches

- Alle Batch-Area-Zuordnungen und Activities entfernt.
- Batch, Movement und Receipt-/Idempotenzmetadaten bleiben als minimaler Bestandsnachweis.
- Gesamtentnahme unverändert; kein Saldo-Rückbuch.

---

## Receipt- und Movement-Nachweis — Minimaldaten

Nach Löschung (auch aller beteiligten Flächen) müssen mindestens erhalten bleiben:

- Inventory Item
- Saved Product Profile / Produkt-Snapshot
- Gesamtentnahme und Einheit
- Anwendungszeitpunkt
- Movement (unverändert)
- Batch-ID
- Idempotenzschlüssel
- Source Event Reference
- Modus und ursprünglicher bestätigter Gesamtwert
- Optional: Hinweis, dass zugehörige Fläche(n) gelöscht wurden

**Nicht dauerhaft erforderlich** (Datenminimierung):

- Ursprünglicher Flächenname im Batch nach Löschung aller Flächen
- Ursprüngliche Teilmengenverteilung nach Löschung aller Flächen

Für **verbleibende** Flächen bleiben Activity-Snapshots (`area_name_snapshot`, `areaSizeSqmSnapshot` in Details) vollständig lesbar.

---

## Pflegegruppenvertrag

- Beim Löschen einer Area wird **nur ihre Membership** entfernt (`care_group_areas`).
- Andere Memberships und Areas bleiben **unverändert**.
- Die Care Group wird **nicht** kaskadierend gelöscht, nur weil eine Area gelöscht wurde.
- **Ist-Verhalten heute:** Trigger `care_group_areas_prune` löst Gruppen mit weniger als zwei Mitgliedern auf — die verbleibende Fläche wird **nicht** gelöscht oder verändert; nur die Gruppe verschwindet.
- Ob eine Care Group mit **nur einer verbleibenden Fläche** fachlich bestehen bleiben oder später automatisch aufgelöst wird: **offene Folgeentscheidung** — in diesem Block **nicht** festgelegt.
- Historische Anwendungen speichern Care Group höchstens als Auswahlherkunft (`careGroupId`-Snapshot); spätere Care-Group-Änderung/-Löschung verändert keine andere Area und keine Bestandsbewegung.

## Kanonische Area-ID-Sortierung

Für Mehrflächenverteilung, Primary-Activity-Auswahl und SQL/TypeScript-Konsistenz ([DL-031](./dl-031.md)):

- Normalisierte **lowercase** UUID-Zeichenfolge
- **Ordinaler** Zeichenvergleich (`<` / `>`), **keine** localeabhängige Sortierung
- SQL: `ORDER BY lower(area_id::text)`
- TypeScript: expliziter Vergleich normalisierter Strings in `fertilizerMultiAreaApplicationCore.ts`

## Auswirkungen auf die Mehrflächenmigration

Vor Implementierung von `fertilizer_application_batches` / `fertilizer_application_areas`:

1. FK-Regeln gemäß obiger Tabelle anlegen.
2. `delete_area`-RPC (Arbeitstitel) planen — löst heutige Blocker (Receipt-RESTRICT, Immutability-Trigger).
3. DL-030-Einzelflächen-Receipt: `area_id`-FK für Flächenlöschung anpassen (`SET NULL` + Snapshots in `result_jsonb`, oder kontrollierte Receipt-Bereinigung im RPC).
4. Keine Neuberechnung von Batch- oder Movement-Mengen bei Area-Löschung.
5. Journal-Read-Pfade filtern gelöschte Flächen implizit (keine Activity mehr).

## Alternativen

| Alternative | Warum nicht |
|-------------|-------------|
| Soft Delete / Archiv standardmäßig | Widerspricht Produktentscheid; `archived_at` bleibt technisches Feld, nicht Standard-Löschpfad |
| Batch mit Area löschen | Zerstört Bestandsnachvollziehbarkeit; Rückbuchungsrisiko |
| Movement-Menge reduzieren | Verfälscht Ledger; verboten |
| Tombstone-Batch-Area-Zeilen (Modell B) | Datenminimierung; widerspricht „Fläche dauerhaft löschen“ |
| Care Group als Löschdomäne | Würde andere Flächen indirekt betreffen |
