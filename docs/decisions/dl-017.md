| **Kurzbeschreibung** | Dünger-Enrichment-Jobs hybrid in `fertilizer_enrichment_jobs`; server-only Zugriff; kein roher Session-Wert in DB/JSONB; Session-Lookup über HMAC-`session_access_hash`. |

---

## Kontext

Phase 3e implementiert den Server-Service für Start, Status, Additional Source und Cancel mit einem injizierbaren In-Memory-Repository. Für produktive Netlify-Functions und Cross-Request-Fortsetzung fehlt Shared Storage.

Ohne verbindliche Persistenzentscheidung bestünde die Gefahr:

- interner Fortsetzungsdaten in öffentlichen API-Responses,
- paralleler fachlicher Zustandswahrheiten in relationalen Spalten,
- direkter Client-Zugriff auf technische Job-Records,
- **persistierter roher Session-IDs** als wiederverwendbarer Sitzungsnachweis,
- oder produktiver Aktivierung ohne echtes Shared Storage.

---

## Entscheidung

Greenkeeper persistiert **`FertilizerEnrichmentJobRecord`** in **einer** Tabelle `public.fertilizer_enrichment_jobs` mit **hybridem** Modell (Option C):

### Relational

Technische Identität, Zugriff, Idempotenz, Revision, Zeit (`expires_at`).

### JSONB

- `job_json` — öffentlicher `FertilizerEnrichmentJob` (**sanitisiert**)
- `orchestration_input_json` — interner Fortsetzungsinput (**sanitisiert**)

### Session-Zugriff (verbindlich)

1. **Rohe `sessionId` wird niemals persistiert** — weder relational noch in JSONB.
2. Persistiert wird ausschließlich **`session_access_hash`** — relational, serverintern.
3. Ableitung: **`HMAC-SHA-256(server_secret, session_id)`** — kein ungesalzener SHA-256-Hash.
4. Secret ausschließlich in der Serverumgebung; **nicht** in DB, Client oder Record.
5. **`FertilizerEnrichmentAccessContext` bleibt unverändert** — Domain darf `sessionId` im Arbeitsspeicher/Request enthalten.
6. Mapping **`sessionId` → `session_access_hash`** erfolgt **ausschließlich** an der persistenten Repository-Grenze.
7. **`session_access_hash` ist kein öffentlicher Vertrag** — erscheint nicht in API-Responses, Logs, Fehlern oder Metriken.
8. **`session_access_hash` wird nie als Client-Input akzeptiert.**

### Authenticated-Zugriff

- `access_kind = authenticated_user`
- `user_id` gesetzt, `session_access_hash` leer

### Verbindliche Regeln (allgemein)

1. **`job_json.result` ist die einzige fachliche Zustandsquelle** — kein separates relationales Statusfeld.
2. **`FertilizerEnrichmentJobRecord` bleibt serverintern** — API liefert nur `{ job: FertilizerEnrichmentJob }`.
3. **Zugriff ausschließlich serverseitig** — Netlify Functions mit Service Role; Service validiert Request-Access-Context; RLS deny-by-default.
4. **Optimistic Locking über `revision`** — konkurrierende Updates dürfen nicht still verloren gehen.
5. **Start-Idempotenz** über partielle Unique-Indizes:
   - `(user_id, idempotency_key)` für `authenticated_user`
   - `(session_access_hash, idempotency_key)` für `session`
6. **Additional-Source-Retry** über `last_source_provision_idempotency_key` — keine Provision-Historie-Tabelle in v1.
7. **Keine produktiven Enrichment-Functions ohne persistentes Repository** — kein In-Memory-Fallback in Production.
8. **Kein Save, kein Bestand, keine Katalog-Promotion** durch Job-Persistenz.
9. **Sanitization vor Persistenz** — keine Rohdokumente, Bilder, Stacktraces; **keine Session-ID in JSONB** (`job_json`, `orchestration_input_json`).
10. **Secret-Rotation** ist in v1 **keine** Implementierungspflicht — stabiles Environment-Secret; Rotation spätere Betriebsentscheidung ohne `session_hash_version`-Spalte in v1.

---

## Begründung

| Kriterium | Hybride Ein-Tabelle-Lösung |
|-----------|----------------------------|
| Anschluss Phase 3e | Record ↔ Zeile 1:1 |
| Sicherheit | Access-Spalten + HMAC statt roher Session-ID |
| Datenschutz | Kein wiederverwendbarer Session-Schlüssel in DB |
| Einfachheit | Keine Run-/Source-Normalisierung ohne Query-Bedarf |
| Schemaevolution | JSONB + `record_schema_version` |
| Wartbarkeit | Ausreichend für Single-Owner-Produkt |

Vollnormalisierung (Option B) würde fachliche Pipeline-Ergebnisse duplizieren. Rohe Session-Speicherung würde bei DB-Leak wiederverwendbare Sitzungsnachweise exponieren.

---

## Alternativen

| Option | Warum nicht |
|--------|-------------|
| **A — rein JSONB** | Idempotenz/Cleanup ohne Schlüsselspalten unsauber |
| **B — voll normalisiert** | Doppelte Zustandswahrheit; höherer Implementierungsaufwand ohne Nutzen |
| **Rohe `session_id` in DB** | Datenschutzrisiko; wiederverwendbarer Sitzungsnachweis |
| **SHA-256(session_id) ohne Secret** | Rainbow-/Lookup-Angriffe; verboten |
| **Clientseitiger Hash** | Secret-Leakage; nicht server-only |
| **In-Memory in Production** | Kein Cross-Request; irreführende serverlose Illusion |
| **Client-RLS auf Jobs** | Leakt technische Fortsetzungsdaten |

---

## Konsequenzen

- Migration und Repository folgen in Phase 4b–4c **nach** dieser Dokumentation.
- Mapping-Schicht muss JSONB vor Schreiben sanitizen.
- `findByIdempotencyKey` für Session leitet Hash aus Request-Kontext ab.
- Produktive Netlify-Endpunkte erst in Phase 4e.
- Cleanup löscht Hash mit Record — keine Hash-Historie.
- Session-scoped Jobs erhalten kürzere TTL als authenticated Jobs.
