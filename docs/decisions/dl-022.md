## Kontext

[DL-018](./dl-018.md) bis [DL-021](./dl-021.md) regeln **Produktversionen**, **Bestandsbewegungen**, **Bestandsbindung** und **Mengeneinheiten** — jeweils als fachliche Einzelentscheidungen.

Für die spätere **Inventory Foundation** fehlt bisher eine zusammenführende Entscheidung darüber:

- welche **fachlichen Bereiche** getrennt bleiben müssen
- welche **Rolle** Bestand (Inventory Item) und Bewegungen (Inventory Movements) spielen
- wie sich **Produktkatalog** und **Inventory** unterscheiden
- wann ein **Bestand entsteht** — und wann **nicht**
- welche **Grenzen** die Inventory Foundation bewusst setzt

Ohne diese Entscheidung bestünde die Gefahr, Katalog und Bestand zu vermischen, Restmengen direkt zu überschreiben oder beim Speichern einer Produktversion still einen Bestand anzulegen.

---

## Entscheidung

### Trennung der Verantwortlichkeiten

Greenkeeper trennt **strikt** zwischen:

1. **Produktkatalog / Produktversionen**
2. **persönlichem Bestand**
3. **Bestandsbewegungen**

Diese Bereiche haben **unterschiedliche Verantwortlichkeiten**.

| Bereich | Frage |
|---------|-------|
| **Produktkatalog / Produktversion** | Welche Dünger existieren? |
| **Inventory (persönlicher Bestand)** | Welche Mengen einer **konkreten Produktversion** besitzt der Nutzer **aktuell**? |

**Verbindlich:** Inventory ist **kein** Katalog.

---

### Fachliche Hierarchie

```
Produktfamilie
        ↓
Produktversion
        ↓
Bestand (Inventory Item)
        ↓
Bestandsbewegungen (Inventory Movements)
        ↓
Anwendung
```

Jede Ebene hat eine **eigene Bedeutung**.

**Keine** Ebene darf durch eine andere **ersetzt** werden.

---

### Inventory Item (Bestand)

Ein **Bestand** (Inventory Item) repräsentiert eine **konkrete verfügbare Menge** einer **konkreten Produktversion** ([DL-018](./dl-018.md), [DL-020](./dl-020.md)).

Ein Bestand ist **immer** gebunden an:

- eine **unveränderliche Produktversion**
- eine **Produktform**
- eine **definierte Einheit** nach [DL-021](./dl-021.md)
- eine **verfügbare Menge** (abgeleitet aus Bewegungen)

**Beispiel:**

| Feld | Wert |
|------|------|
| Produktversion | Stressmanager Granulat 0-0-30 |
| Bestand | 25 kg |

---

### Bestand ist nicht das Produkt

Ein Bestand ist **nicht**:

- der Produktname
- die Produktfamilie
- der Herstellerartikel allgemein
- eine Katalogdefinition

**Nicht:**

> „Stressmanager Bestand“

**Sondern:**

> „Stressmanager Granulat 0-0-30, 25 kg“

---

### Inventory Movement (Bestandsbewegung)

**Bestandsbewegungen** (Inventory Movements) sind die **einzige Quelle** für Mengenänderungen ([DL-019](./dl-019.md)).

Die Menge eines Bestands wird **nicht direkt** verändert.

**Beispiele:**

| Bewegung | Grund (konzeptionell) |
|----------|----------------------|
| +25 kg | `purchase` (Kauf) |
| −3 kg | `application` (Anwendung / Verbrauch) |
| −5 kg | `gift_given` (Verschenkt) |

Die **konkrete technische Kodierung** von Bewegungsgründen ist **nicht** Gegenstand dieses Decision Logs.

---

### Aktueller Bestand

Der **aktuelle Bestand** ergibt sich aus der **Summe aller Bewegungen**.

**Nicht:** ein Feld mit manuell überschriebener Restmenge.

**Beispiel:**

| Bewegungen | |
|------------|---|
| +25 kg | |
| −10 kg | |
| −5 kg | |
| **Aktueller Bestand** | **10 kg** |

---

### Korrekturen

Korrekturen **verändern keine historischen Bewegungen** ([DL-019](./dl-019.md)).

Eine Korrektur erfolgt **ausschließlich** über eine **neue Gegenbuchung**.

**Beispiel:**

| Schritt | Bewegung |
|---------|----------|
| Fehlerhafte Erfassung | +20 kg |
| Korrektur | −5 kg (Gegenbuchung) |

**Nicht:** Änderung der ursprünglichen Bewegung.

---

### Verbindung zur Anwendung

Eine spätere **Anwendung** verbraucht **immer** aus einem **konkreten Bestand** ([DL-019](./dl-019.md), [DL-020](./dl-020.md)).

**Nicht:**

> „3 kg Stressmanager verwendet“

**Sondern:**

> „3 kg aus Bestand X der Produktversion Y verwendet“

Damit bleiben **historische Anwendungen reproduzierbar**.

---

### Bestandsanlage

Das **Erkennen** oder **Speichern** einer Produktversion erzeugt **nicht automatisch** einen Bestand.

**Grund:** Ein bekanntes Produkt bedeutet **nicht automatisch** Besitz.

**Beispiel:**

| Situation | Ergebnis |
|-----------|----------|
| Nutzer fotografiert einen Dünger im Baumarkt | Produkt erkannt: **Ja** |
| | Bestand: **Nein** |

Ein Bestand entsteht erst durch eine **bewusste Bestandsanlage** — zum Beispiel Kauf, Geschenk, manuelle Erfassung eines vorhandenen Bestands oder vergleichbarer Zugang ([DL-019](./dl-019.md)).

**Verbindlich:** Ein erfolgreicher **Product-Profile-Save** nach Enrichment speichert **Produktwissen** — **keinen** automatischen Bestand ([DL-012](./dl-012.md), [GA-014](../architecture/ga-014.md)).

---

### Nullbestand

Ein Bestand wird bei Menge **0 nicht gelöscht** ([DL-021](./dl-021.md)).

Er bleibt **historisch erhalten**.

**Beispiel:**

| | |
|---|---|
| 25 kg Zugang | |
| 25 kg Verbrauch | |
| **Ergebnis** | **0 kg Bestand** |

Der Bestand kann später als **nicht mehr verfügbar** dargestellt werden — die **Historie** bleibt bestehen.

Diese Entscheidung umfasst **ausdrücklich nicht**:

- Datenbankmodell
- Tabellenstruktur
- API
- UI
- Lagerorte
- Preise
- Händler
- Kaufhistorie
- Chargen

- Implementierung der Bestandsberechnung

---

## Begründung

- **Klare Verantwortlichkeiten:** Katalog, Bestand und Bewegungen erfüllen unterschiedliche fachliche Zwecke ([DL-012](./dl-012.md)).
- **Keine falsche Besitzannahme:** Erkennung oder Produktversion-Save ≠ automatischer Bestand.
- **Auditierbare Historie:** Bewegungen als einzige Mengenquelle schützt Nachvollziehbarkeit ([DL-019](./dl-019.md)).
- **Reproduzierbare Anwendungen:** Verbrauch aus konkretem Bestand bindet Anwendung an Produktversion ([DL-020](./dl-020.md)).
- **Grundlage ohne Vorimplementierung:** Inventory Foundation kann später auf verbindlichen Grenzen aufsetzen — ohne vorzeitige Technikentscheidungen.

---

## Alternativen

| Alternative | Warum nicht gewählt |
|-------------|---------------------|
| Inventory als Erweiterung des Produktkatalogs | Vermischt globales Wissen und persönlichen Besitz |
| Restmenge als direkt editierbares Feld | Bricht Bewegungshistorie und Audit ([DL-019](./dl-019.md)) |
| Automatischer Bestand beim Product-Profile-Save | Erkennung ≠ Besitz; würde falsche Bestände erzeugen |
| Bestand bei Menge 0 löschen | Verliert Historie und Anwendungsbezug ([DL-021](./dl-021.md)) |
| Anwendung nur auf Produktname | Nicht reproduzierbar bei mehreren Beständen oder Versionen |

---

## Konsequenzen

- Die **Inventory Foundation** baut auf drei getrennten fachlichen Bereichen auf: Produktversion, Inventory Item, Inventory Movement.
- **Bestände** referenzieren **genau eine** Produktversion mit fester Produktform und Basiseinheit ([DL-020](./dl-020.md), [DL-021](./dl-021.md)).
- **Mengenänderungen** erfolgen **ausschließlich** über Bewegungen; Korrekturen per Gegenbuchung ([DL-019](./dl-019.md)).
- **Product-Profile-Save** und **Bestandsanlage** bleiben **getrennte** fachliche Schritte.
- **Nullbestände** bleiben erhalten.
- Detailliertes Modell in [GM-008](../model/gm-008.md) und technische Regeln in [GA-012](../architecture/ga-012.md) bleiben unter Einhaltung dieser Grenzen — **ohne** dass DL-022 Implementierung festlegt.
